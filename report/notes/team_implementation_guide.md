# ER Defense Validator — Team Implementation Guide

## 1. Project Objective

This project evaluates three automated methods for detecting logical design errors in Information Engineering/Crow's-Foot Entity-Relationship (ER) designs.

All three methods perform the same task:

> Given an ER design containing entities, attributes, primary keys, foreign keys, relationships, cardinalities, participation constraints, and textual design requirements, determine whether the design is logically valid. If it is invalid, identify the corresponding error type or error types.

The three methods being compared are:

1. Deterministic Rule-Based Validator
2. Constraint-Solver Validator using Z3
3. LLM-Based Validator

The methods must use the same input cases, the same seven-error taxonomy, and the same prediction-output format so their performance can be compared directly.

Do not create a separate dataset or separate input format for an individual method.

# 3. Shared Error Taxonomy

Every method must use these exact error labels.

## E01 — FK_TARGET_NOT_KEY

A foreign key references an attribute that is not a primary key or candidate/unique key.

## E02 — FK_WRONG_ENTITY

A foreign key points to the wrong parent entity relative to the declared relationship or design requirements.

## E03 — COMPOSITE_FK_INCOMPLETE

A parent has a composite identifier, but the child contains or maps only part of the required foreign key.

## E04 — CARDINALITY_UNIQUENESS_CONFLICT

The declared relationship cardinality conflicts with the key or uniqueness structure.

Example: a relationship is declared as one-to-one, but the child foreign key is not unique.

## E05 — PARTICIPATION_OPTIONALITY_CONFLICT

A mandatory relationship is represented using a nullable foreign key or another structure that permits optional participation.

## E06 — IDENTIFYING_RELATIONSHIP_KEY_ERROR

A relationship is identifying, but the parent identifier is not correctly propagated into the child's primary key.

## E07 — MISSING_REQUIRED_RELATIONSHIP

A design requirement specifies that two entities must be related, but the required relationship or corresponding foreign-key connection is absent.

These exact labels are defined centrally in:

```text
src/core/constants.py
```

Do not rename them inside an individual method.

# 5. Common Prediction Contract

Every method returns the same conceptual output:

```json
{
  "case_id": "VALID_0001",
  "method": "rule_based",
  "predicted_valid": true,
  "errors": [],
  "runtime_ms": 2.31
}
```

An invalid prediction follows this structure:

```json
{
  "case_id": "INVALID_E01_TEST_001",
  "method": "rule_based",
  "predicted_valid": false,
  "errors": [
    {
      "error_type": "FK_TARGET_NOT_KEY",
      "entity": "ORDER",
      "attribute": "customer_id",
      "relationship": "customer_order",
      "message": "Foreign key references a non-key attribute."
    }
  ],
  "runtime_ms": 3.02
}
```

When:

```text
predicted_valid = true
```

the `errors` array must be empty.

When:

```text
predicted_valid = false
```

at least one error must be returned.

# 17. AI-Assisted Development Instructions

If an AI coding assistant is used, provide it with the relevant project files and the following constraints.

Tell the AI:

> I am implementing one method inside an existing ER-diagram validation benchmark. Do not redesign the repository, dataset, schemas, error taxonomy, or shared core infrastructure. My method must inherit from `src.core.validator_interface.BaseValidator`, use the existing `Prediction` and `PredictionError` models, accept prediction-safe ER cases without ground truth, and return only the seven error labels defined in `src/core/constants.py`. Do not create a new dataset loader or new result format. My implementation belongs only in my assigned method directory. Raw predictions must conform to `schemas/prediction.schema.json`.

Then identify the assigned method.

For the rule-based method, add:

> Implement the deterministic rule-based validation logic in `src/methods/rule_based/validator.py`. The method name must be `rule_based`. Detect the seven existing taxonomy errors using structural ER rules.

For the constraint-solver method, add:

> Implement the Z3 constraint-solver validation logic in `src/methods/constraint_solver/validator.py`. The method name must be `constraint_solver`. Translate the same ER integrity rules into formal constraints and detect the same seven taxonomy errors.

For the LLM method, add:

> Implement the LLM validation method in `src/methods/llm_based/validator.py` and its reusable prompt in `src/methods/llm_based/prompt.txt`. The method name must be `llm_based`. Ground truth must never be placed in the model prompt. Force the output into the project's existing structured prediction format and restrict error labels to the seven taxonomy labels.
