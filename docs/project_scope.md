# ER Defense Validator — Project Scope

## 1. Project Title

**Automated Detection of Non-Trivial Integrity and Relationship Errors in ER Diagrams: A Comparison of Rule-Based, Constraint-Solver, and LLM-Based Validation**

## 2. Project Line

**Defense Line — Automated Logical Diagram Validation**

The project develops and evaluates automated methods for determining whether an Entity-Relationship (ER) design satisfies predefined logical rules and constraints.

The project focuses on logical design errors rather than simple drawing, formatting, or syntax errors.

## 3. Diagram Type

The project uses one diagram family:

**Information Engineering / Crow's-Foot ER diagrams**

All three validation methods operate on the same ER representation and solve the same validation task.

ORM and UML diagrams are outside the scope of the experimental comparison.

## 4. Validation Goal

Given:

1. an ER design,
2. its entities and attributes,
3. primary-key and foreign-key definitions,
4. relationship cardinalities and participation information, and
5. a set of design requirements,

the validator determines whether the ER design contains non-trivial logical design errors.

The system should identify both:

- whether the design is valid; and
- which specific design errors are present.

## 5. Error Categories

The initial benchmark focuses on the following error families:

- incorrect foreign-key target;
- foreign key referencing a non-key attribute;
- incomplete composite foreign key;
- relationship/cardinality and uniqueness conflict;
- participation/optionality conflict;
- identifying-relationship key propagation error;
- missing required relationship.

The exact labels and definitions are specified in `docs/error_taxonomy.md`.

## 6. Methods

Three methods will solve the same validation task.

### Method 1 — Rule-Based Graph Validator

The ER design is represented as a graph.

Deterministic Python validation rules inspect entities, keys, foreign keys, relationships, cardinalities, participation constraints, and identifying relationships.

### Method 2 — Formal Constraint-Solver Validator

The ER design and design requirements are translated into logical constraints.

An SMT solver such as Z3 checks whether the design satisfies the constraint set and reports violated rules.

### Method 3 — LLM-Based Validator

A large language model receives the normalized ER case and validation requirements.

The model returns a structured prediction identifying whether the design is valid and listing detected errors using the same error taxonomy used by the other two methods.

## 7. Shared Input Requirement

All three methods must receive the same normalized ER case representation.

The authoritative experimental input is JSON.

PlantUML files and rendered PNG diagrams may also be stored for visualization, manual inspection, posters, and examples, but method performance must be evaluated using the same case information.

No method may use information unavailable to the other methods unless that difference is explicitly documented as part of the experimental design.

## 8. Shared Output Requirement

Each method must return the same prediction structure containing:

- case ID;
- method name;
- predicted validity;
- detected error labels;
- affected entities, attributes, or relationships where applicable;
- explanatory message;
- runtime.

The exact output format is defined in `schemas/prediction.schema.json`.

## 9. Dataset Strategy

The benchmark will contain controlled ER cases from multiple application domains, including examples such as:

- university registration;
- healthcare;
- e-commerce;
- library systems;
- hotel reservations;
- banking;
- employee/project management;
- inventory and suppliers.

Valid base designs will be created first.

Invalid cases will then be generated by injecting controlled logical errors from the defined error taxonomy.

The benchmark should contain:

- valid cases;
- single-error invalid cases;
- multi-error invalid cases;
- cases with different diagram sizes and structural complexity.

A small set of manually designed holdout cases may also be included to evaluate generalization beyond automatically generated cases.

## 10. Generalization Requirement

The implementation must not contain case-specific rules such as:

- special handling for a particular entity name;
- hard-coded university, hospital, store, or library entities;
- fixed case IDs;
- fixed relationship names;
- manually encoded answers for individual test cases.

Validation rules must operate on schema structure and constraint information.

## 11. Evaluation

All three methods will be evaluated on the same held-out test cases.

Primary metrics will include:

- Precision;
- Recall;
- F1 score;
- Macro-F1 across error types;
- diagram-level validity accuracy;
- exact error-set accuracy;
- error localization accuracy;
- false-positive rate;
- average runtime per case.

Results will also be reported separately for each error category.

## 12. Experimental Fairness

For a fair comparison:

1. All methods use the same test cases.
2. All methods use the same error taxonomy.
3. All methods produce predictions using the same output schema.
4. Test ground truth is not used during prediction.
5. Evaluation is performed by one shared evaluation pipeline.
6. Any external model settings or prompts are documented.
7. Runtime measurements are recorded consistently.

## 13. Out of Scope

The initial project does not attempt to:

- recognize arbitrary ER diagrams directly from screenshots;
- validate Chen, ORM, and UML simultaneously;
- detect purely cosmetic layout problems;
- perform full database normalization analysis;
- automatically repair every detected error;
- train a large multimodal model from scratch.

These may be discussed as future extensions.
